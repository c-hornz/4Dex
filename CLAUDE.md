# 4Dex — working notes for Claude

Experimental four-spatial-dimensional VR perception engine for Oculus Rift PCVR.
A **perception and navigation instrument first, a maze game second.**

## Read these before doing anything

- `docs/SPEC.md` — the authoritative requirements (32 sections). Answers most
  design questions; don't ask the user what it already specifies.
- `docs/ARCHITECTURE.md` — decisions already made, and *why*.

**The architecture is decided. Do not relitigate it.** If you believe a decision
is wrong, say so in a sentence and keep working under it; don't quietly
substitute a different design.

## Current status

Milestone 0 in progress, on Windows. `src/` holds three engine-free libraries,
Math4D, World4D and Player4D (Player4DState, the §25 focusW / position.w
invariants). They build and `tests/4Dex.Tests` passes (84/84, .NET SDK 10.0.401).
`src/` is also the Unity local package `com.fourdex.core`, so the same sources
compile in Unity, with `noEngineReferences` asmdefs. dotnet output goes to
`artifacts/` (see `Directory.Build.props`) so Unity never sees `obj/`. A new
library under `src/` needs a `.csproj`, an `.asmdef` and a `csc.rsp`.
Namespaces are `FourDex.World` and `FourDex.Player`, not `...World4D` /
`...Player4D`: a namespace named like a class in it would shadow that class from
every other `FourDex.*` namespace.
The Unity project lives at the repo root (URP Blank template, OpenXR 1.18.0,
XR Management 4.7.0). XR is configured by `Assets/4Dex/Editor/XRProjectSetup.cs`
(menu **4Dex > Configure XR**): OpenXR loader on Standalone, Oculus Touch
profile. It is idempotent; rerun it rather than clicking through Project Settings.
`Assets/4Dex/Runtime/XR` has XRRig + HmdPoseSource (camera gets the raw pose
first, then `PoseSampled` fans it out to the 4D mapping). Its invariants are
Unity EditMode tests in `Assets/4Dex/Tests/EditMode`. They have not yet run
against a real headset.
`Assets/4Dex/Runtime` (asmdef `4Dex.Runtime`) wraps the cores for scenes:
`Player4D`, `World4DRegistry` + `Object4DBehaviour` (inspector-authored 4D pose),
and a minimal `ProjectionDriver`, pulled forward from Milestone 1. It places
objects in the player's slice each frame and records signed `DeltaW`; there are
no shaders yet. An object's Unity transform is *output*, overwritten every frame;
author it in 4D. `Debug4D/CoordinateHUD` (goes on the XR camera) is a
head-locked, world-space readout: position, focus, basis vectors +
orthonormality error, raw HMD pose. Its text comes from the pure
`CoordinateReadout.Format`. Unity tests: 15/15 passing.
`Assets/Scenes/Lab4D.unity` (SPEC §23) is generated by
`Assets/4Dex/Editor/Lab4DSceneBuilder.cs` (menu **4Dex > Rebuild Lab4D Scene**).
Change the builder and rerun it rather than hand-editing the scene. Its
`Snapshot` method renders the XR camera's view to a PNG headlessly (needs
graphics, so omit `-nographics`; pass `-snapshotPath <png>`). Use it to check
visual changes. `-playerW <w>` and `-focusW <w>` set the 4D state first.
`docs/images/lab4d-m1-focus*.png` are the reference renders.

**Milestone 1 (W-focus)**: the acceptance test passes on the desktop, both in
tests and in renders. Pieces:
- `src/4Dex.Perception4D`: engine-free mapping from signed W gap to SPEC §11
  band + channels, with swappable curves.
- `PerceptionSettings` asset (`Assets/4Dex/Settings/`): all tuning. Edit it live
  in play; it persists, so it doubles as a saved preset.
- `Phase4D` shader: dither-to-opaque on an object-fixed lattice, phase stripes
  rising for ana and sinking for kata, shimmer from focus mismatch, palette as a
  redundant cue.
- `PhaseRenderer`: puts the channels in each object's property block.
- `ProjectionDriver`: gap from the object's W extent in the viewer's frame.
- HUD: per-object gap/band/V lines.

- Debug tools. Both are head-locked, built by `Debug4D/DebugPanel`, and go on
  the XR camera:
  - `WSliceViewer` (SPEC §20; V toggles): each object's W extent as a bar on
    the player's W axis, with focus and the A/B/C bands shaded around it.
  - `RuntimeParameterPanel` (SPEC §21; Tab shows, Up/Down select, − / =
    adjust, Shift ×10): every parameter in `PerceptionParameterList`. Edits go
    into the settings asset and persist. It reads no input itself;
    DesktopTestMode drives it today, and M4 controllers can call the same
    methods. Later milestones add their parameters to `PerceptionParameterList`.

The mapping runs in C#, not HLSL; see ARCHITECTURE §6. Milestone 1 is complete.

**Milestone 2 (ana/kata translation)** acceptance is met by the existing code:
R/F move `position.w`, objects' gaps go to zero as you reach them, and focus
and W movement stay independent. `ProjectionDriverTests` and
`PlayerStateTests` cover it, and `lab4d-m2-player-w1.png` shows it (player at
w = +1 with focus 0 looks like focus +1, but the HUD differs).

**Milestone 3 (4D rotation)**: the acceptance test passes. Rotating XW/YW/ZW
turns the perceived 3D subspace, and `position.w` is unchanged:
`RotationTests`, plus `lab4d-m3-xw45.png` and `lab4d-m3-xw90.png`. Pieces:
- `Rotor4.Log()`: the six simultaneous plane angles, the inverse of
  `FromBivector`, taking the smaller-angle side of the double cover.
- `Player4D/RotationMonitor`: orientation angles, plus a smoothed per-plane
  rate in the player's own planes, measured from successive orientations, so
  it works for any input source. The HUD shows ROTATION and RATE lines
  (SPEC §20).
- `ProjectionDriver` sizes each object from its 4D box's extent along each
  footprint axis. That's exact for 3D rotations; through W, the extent turned
  into X shows as width.
- Ordinary planes: the 4D view's XZ is on the arrows. XY/YZ come from the head
  (pitch/roll) and get mapped in M4.

Snapshot `-rotXW 90` (any plane) turns the player; `-defaultPerception`
renders with default tuning, so references don't depend on tuning saved in the
settings asset.

**Milestone 4 (generalized input mapping)**: the acceptance test passes on the
desktop. `HeadMappingTests.SameHeadPitch_ThreeConfigurations_NoCodeChange`
shows that only the selected profile makes head pitch drive ordinary pitch, YW,
or 70/30. Semantics are in ARCHITECTURE §8a: perceived fraction, delta/steer
default, eye pivot. Pieces:
- `src/4Dex.Input4D` (namespace `FourDex.InputMapping`, not `FourDex.Input`,
  which would shadow `UnityEngine.Input`): `MappingEngine`, `InputBinding`
  shaping (dead zone, curve, gain, invert, clamp), `MappingPresets` (the six
  SPEC §6 profiles).
- Profile assets in `Assets/4Dex/Settings/Mapping/`. The builder creates
  missing ones and never overwrites tuned ones.
- `HeadMappingDriver` (on World4D): offsets from a recentred neutral, in the
  neutral facing. It gives the comfort controls: freeze, disable, return to
  CLASSIC.
- Desktop: P profile, X freeze, C recenter, Q/E simulated roll, T/G simulated
  lean. Backspace also returns to CLASSIC.
- HUD: `MAPPING` monitor lines (SPEC §20). The key legend and input monitor
  moved to a separate help panel above the lab (H hides it).
- Parameter panel: `map:` entries (profile, comfort toggles, W gains,
  pitch/roll/lean weights, mode and dead zone). It scrolls.

**Milestone 5 (survey mode)**: the acceptance test passes. Hold Space and
neighbouring W geometry becomes perceptible, with signed cues preserved:
`PerceptionDriverTests.Survey_*`, `SurveyTests`, and
`lab4d-m5-survey-off/on.png`. Survey is one more input to the same
`PerceptionModel.Evaluate`:
- Survey widens visibility, density and bands B/C (`SurveyWidth`,
  `SurveyBandScale`). Band A stays fixed, so nothing becomes LOCAL by
  surveying.
- Coherence and phase amplitude stay tied to real focus, so surveyed
  neighbours read as shimmering echoes, not local geometry. The sign channels
  are untouched.
- `SurveyRamp` eases it in and out (`SurveyRampSeconds`).
- The lab gained E/F at w = ±2, OUTSIDE normally, for survey to reveal.
- Snapshot `-survey 1`.

**Milestone 6 (4D shadow prototype)**: the acceptance test passes. Objects
outside the visible W focus still cast, and their shadows follow signed W
distance and focus: `ShadowTests`, `PerceptionDriverTests.HiddenObjects_*`
and `FocusingOnAHiddenOccluder_*`, plus
`lab4d-m6-shadow-hidden/focused.png`.
- `ShadowModel` (engine-free): W gap → strength (fades over `WRange`, far
  wider than the visibility bands, so unseen objects cast), coherence
  (`FocusWidth`, SPEC §14), signed tint, shimmer, edge softness.
- `ProjectionDriver` uploads a bounded occluder list (16, strongest first) as
  shader globals; casting is deliberately not gated on being rendered.
- `Phase4DCommon.FourDexShadowField` evaluates it per pixel: darkness, hue by
  ana/kata, penumbra growing with softness, flicker from shimmer. Unity's own
  shadows are still unused.
- The floor uses Phase4D so it receives; the light is steeper and the floor
  larger so shadows land in view. Snapshot `-lookDown`.
- Parameters are in `PerceptionSettings.Shadow`, with panel entries.

**Milestone 7 (advanced shadow behaviour)**: ripple, echoes and view-dependent
shear, all live-tunable (`ShadowRippleTests`,
`PerceptionDriverTests.RotatingThroughW_Shears*` and `ThickObjects_*`, renders
`lab4d-m7-ripple/shear/echo.png`).
- **Ripple** (§15): rings across the shadow; frequency rises with |W gap|,
  travel is outward for ana and inward for kata, amplitude follows occlusion
  strength. `InvertRipple` swaps the convention without touching the tint.
- **Shear** (§16): the shadow shifts along `wLean`, the direction world W leans
  into the viewed 3-space (`toViewer.Apply(UnitW).Xyz()`). It is exactly zero
  in a conventional view, so rotating through W slides ana and kata shadows
  apart.
- **Echoes** (§17): a W-thick occluder casts `EchoCount` copies spread along
  that same direction by its W extent; the spread collapses as focus arrives.
  Cost is occluders x echoes x pixels, so both are bounded (16 x 5).
- HUD object lines now carry the shadow columns (strength, ring frequency,
  in/out, echo spread): SPEC §20's shadow debug view.

**Milestone 8 (4D cells)**: the acceptance test passes. The player navigates a
hand-authored cell structure through ordinary directions and ana/kata, and
walls stop them (`CellCollisionTests`, `MazeRuntimeTests`, renders
`lab4d-m8-cells-*.png`).
- `CellCollision` (engine-free): resolves a move axis by axis against
  `Maze4D`'s faces, so you slide along walls, cannot tunnel at speed, and W is
  blocked exactly like X/Y/Z.
- `Player4DState.MovementFilter`: the hook collision plugs into, so walking,
  ana/kata and head-driven movement are all constrained without the player
  state knowing about mazes. `RotateLocalAbout`'s pivot shift bypasses it.
- `MazeRuntime` (on World4D): grid size, cell size, the authored openings, the
  player radius; it installs the filter, reports the current cell and its exits
  into the HUD footer, and produces the wall faces.
- `Assets/Scenes/Cells4D.unity` (menu **4Dex > Rebuild Cells4D Scene**): a
  2x1x2x2 grid of 3 m cells whose route needs ana and kata. Walls are ordinary
  4D objects, so a wall one cell away in W is a dithered echo you can survey.
  Snapshot `-scene Cells4D`, `-playerX/-playerZ`.
- HUD and W-slice cap their per-object lists (nearest in W, with a "+N more"
  note), since a maze has dozens of walls.

**Milestone 9 (procedural 4D maze)**: done, and with it every milestone in
SPEC §24. `MazeGenerator4D` carves a randomised depth-first maze over the 4D
adjacency graph, where ana and kata are two of a cell's eight neighbours:
- `Seed` (same seed, same maze), `WBias` (how much the carve prefers W over
  ordinary directions), `ExtraOpenings` (loops; 0 leaves a perfect maze).
- Connected by construction, and `IsConnected` / `CountOpenings` check it:
  `MazeGeneratorTests` covers 25 seeds, awkward shapes, the spanning-tree edge
  count, determinism, the W bias, and the boundary holding.
- `MazeRuntime._generate` switches a scene from authored openings to carving.
- `Assets/Scenes/Maze4D.unity` (menu **4Dex > Rebuild Maze4D Scene**): 3x1x3x2
  cells, seed 4, WBias 0.65, 2 extra openings. 19 openings, 7 through W.
- Snapshot `-scene Maze4D`, and `-cameraY` for a map view from above, since
  mazes have no ceilings.

## Non-negotiables

These are load-bearing. Violating one is a design regression, not a shortcut.

1. **Math4D and World4D never reference `UnityEngine`.** They are plain .NET
   libraries with their own `Vec4` and quaternion, so the mathematical core is
   testable without Unity and SPEC §3's separation is enforced by the compiler.
2. **HMD pose fans out to two independent consumers.** It drives the camera
   transform unmodified (stereo must stay correct), *and* separately feeds the
   4D mapping system, whose output changes only how geometry is **projected** —
   never the camera matrices. No `TrackedPoseDriver` on the camera.
3. **Move / Rotate / Focus stay three distinct operations** (SPEC §7).
   `position.w`, the XW/YW/ZW view basis, and `focusW` are independent. Never
   collapse them into one "fourth dimension" control, and never let one
   implicitly change another.
4. **Orientation is a `Rotor4` = pair of unit quaternions**, not a 4x4 matrix
   basis. `Basis4` is a derived read-only view for debug display and shader
   upload. See `docs/ARCHITECTURE.md` §4 for the derivation and the
   plane-to-generator table.
5. **Signed deltaW must stay perceptually recoverable.** Ana and kata must be
   distinguishable without relying on colour — direction, frequency, coherence
   and density carry it too (SPEC §9).
6. **Every visual effect encodes information** (SPEC §27). Phase, ripple,
   shimmer and density are not decoration. No meaningless psychedelic noise.
7. **Parameterize, don't hardcode.** Perceptual mappings live in configuration
   assets exposed at runtime, never in bespoke per-experiment scripts.

## Conventions

- `P = (x, y, z, w)`; `+W = ana`, `-W = kata`.
- Quaternion mapping for rotors: `q = w + xi + yj + zk` — **w is the real part.**
- Comment *why* a mathematical transformation exists, not every line of C#.

## Building and testing

The math core builds and tests anywhere, without Unity or a headset:

```
dotnet test 4Dex.Core.sln
```

(Name the solution explicitly: Unity generates its own `4Dex.slnx` at the root.)
Namespaces are `FourDex.*`, since C# identifiers cannot start with a digit.

Do this before touching Unity-side code — a failing invariant there will
otherwise surface as a baffling rendering bug (SPEC §20).

## Debugging

4D bugs routinely look like rendering bugs. Debug tooling is a first-class
feature, not an afterthought — build the coordinate HUD, basis display and
freeze controls early (SPEC §20, §21).
